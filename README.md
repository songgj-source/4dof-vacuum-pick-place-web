# 4축 진공흡착 로봇팔의 비전 기반 Pick & Place 시스템 구현

4축 로봇팔과 진공흡착 장치를 활용해 물체를 인식하고 트레이의 지정된 칸으로 옮기는 시스템을 구현했습니다. RGB-D 카메라의 관측값을 로봇 좌표로 변환하고, 역기구학으로 관절 목표를 계산하여 집기·운반·놓기·HOME 복귀를 연결했습니다.

## 동작 흐름

![소프트웨어 흐름](portfolio/assets/software_pipeline.png)

1. **인식**: HOME 자세에서 Astra로 촬영합니다. 깊이로 책상 평면을 맞춘 뒤 평면 위로 솟은 덩어리를 찾고, 색 비율로 물체 3종을 구분합니다. 트레이는 벽 깊이와 손글씨 숫자(1·2·3)로 칸 위치와 번호를 구합니다. 등록하지 않은 새 물체는 빈 장면의 깊이 기준과 비교해 찾고, 윗면 높이·크기·평평한 흡착 지점을 측정합니다.
2. **좌표 변환**: 물체 윗면 중심 픽셀을 카메라 광선으로 바꾸고, 물체 윗면 높이의 평면과 만나는 점을 로봇 base 좌표로 씁니다. 접촉 높이는 자로 잰 물체 높이에 흡착컵 보정값을 더해 정합니다. 깊이 측정은 ±3 mm 오차가 있어 높이에는 쓰지 않습니다.
3. **역기구학**: 공구 pitch를 정해 4축 평면 IK를 해석적으로 풉니다. 관절 한계와 링크 높이(책상 충돌)를 먼저 검사하고, 도달할 수 없는 목표는 계획 단계에서 거부합니다.
4. **접근·흡착**: 120 mm와 70 mm 높이에서 차례로 멈춰 접근 오차를 5 mm 기준으로 검사·보정합니다. 이어서 60 pulse/s로 천천히 내려가 흡착하고 20 mm 들어 올립니다.
5. **운반·놓기**: base 기준 극좌표로 보간해 칸 위로 옮깁니다. 칸 벽에 닿지 않도록 필요하면 공구를 최대 50°까지 기울이고, 칸 안으로 내린 뒤 배기해 놓습니다.
6. **HOME 복귀**: 복귀 경로 전체를 명령 전에 검사한 뒤 접어서 복귀합니다. 도착 후 정지를 확인하고 임시 게인을 원래 값으로 돌립니다.

## 시스템 구성

![시스템 구성](portfolio/assets/system_architecture.png)

| 신호 | ESP32 | 연결처 |
|---|---|---|
| 펌프 방향 A | GPIO26 | L9110S A-1A |
| 펌프 방향 B | GPIO25 | L9110S A-1B |
| UART RX (배선만, 미사용) | GPIO33 | 서보 어댑터 TX |
| UART TX (배선만, 미사용) | GPIO32 | 서보 어댑터 RX |
| 공통 GND | GND | (−) 레일 |

PC는 USB 115200 baud로 펌프를 제어합니다(`p` 흡착 / `d` 배기 300 ms / `s` 정지 / `q` 식별). 배선도와 펌웨어는 [`하드웨어 설명/`](하드웨어%20설명/README.md)에 있습니다.

## 주요 문제 해결

| 문제 | 원인 | 수정 | 검증 |
|---|---|---|---|
| 먼 위치일수록 옆으로 최대 16.5 mm 어긋난 집기 | 카메라 좌표와 팔 모델의 위치별 오차 | 카메라 이동 후 팔 FK를 자 삼아 8점으로 카메라 자세 재보정, 팔 영점 보정 | 맞춤 RMS 3.0 mm, 교차검증 RMS 6.2 mm, 기구학 잔차 5.97 → 1.28 mm |
| 카메라 재보정 뒤 옛 위치 보정이 중복 적용됨 | 옛 카메라 오차를 메우던 앵커 오프셋·접선 보정이 남음 | 좌표 계산을 자세 추정·평면 투영·경험 보정으로 나누고, 옛 보정 두 가지를 0으로 끔(원래 값 보관) | 재보정 후 상자 중앙 접촉 확인 |
| 운반 중 팔 떨림 | base 임시 게인 P32, 직선 경로에서 base 저속 stick-slip | base P16 복원, 극좌표 보간으로 base를 일정 속도로 회전 | 실물에서 떨림 해소 확인 |
| 정지했는데 다음 동작 인계가 거부됨 | 하중으로 남는 3–6 pulse 편차를 움직임으로 오판 | 목표 불변·위치 안정·편차 크기를 따로 검사하고 관절별 하중 오프셋으로 기록 | 모의 시험 통과, 실물 효과 미확인 |
| 트레이 칸 위치 오인·인식 실패 (물체가 벽에 걸림, 칸이 가려짐) | 깊이에 벽 일부만 보여 방향이 12° 틀어짐, 물체가 칸 바닥을 가림 | 색 실루엣으로 긴 축 추정, 빈 트레이 기준 프레임 저장 후 모서리 정합으로 이동·회전 보정(40 px·6° 넘으면 재인식) | 정육면체 → 2번 칸 실물 성공, 실제 프레임 9 px·−1.3° 이동을 잔차 0.3 px로 측정 |
| 등록하지 않은 새 물체가 계획·재확인 단계에서 계속 거부됨 | 깊이 그림자·벽 번짐으로 칸을 68×96 mm로 과소 계산(실제 92×100), 재확인 기준이 측정 흔들림보다 빡빡, 운반 높이 상한 120 mm, 변수 덮어쓰기 버그 | 칸 경계를 실측 사각형으로 두고 깊이 0은 장애물로 보지 않음, 평평함 5–95% 판정, 재확인 허용치 완화, 운반 높이 130 mm, 변수 분리 | 36 mm 물체를 2번 칸에 넣기 실물 성공(74 s), 반복 성공률은 미확인 |
| 수직 자세로 닿지 않는 위치, 중간 경로 실행 불가 | 4축 팔의 자세 제약 | 접근·호버·접촉을 같은 IK로 검사, 기울기 0–20° 탐색, 벽·주변 물체 높이로 운반 경로 구성 | 45° 기울여 1번 칸에 놓기 실물 사용 |
| Raspberry Pi로 옮긴 뒤 하강·들기에서 팔이 끊겨 떨림 | 느린 이동이 틱마다 서보 4개 × 레지스터 9개를 하나씩 읽어(왕복 36번, Pi 15.9 ms) 13.3 ms 틱을 넘김. 넘기면 다음 틱이 한 주기 더 밀려 39 ms마다 2 pulse씩 가다 서기(움직일 관절이 틱의 55–68% 정지) | 고정값(ID·모델·한계·영점)은 이동 시작 때 전체 읽기로 확인해 두고, 이동 중에는 관절당 34바이트 한 번 읽기(Pi 3.1 ms) | 모의 시험 통과, Pi에서 읽기 시간 실측. 실물 떨림 재측정은 미확인 |
| 물체를 든 채 올리며 기울이다 "집은 자리 위를 벗어남"으로 정지(물체는 정확히 집은 상태) | 느린 구간은 서보 속도 레지스터 40을 써서 관절이 초당 약 56–60 pulse에 묶임. 경로는 그 두 배를 요구해 어깨가 계속 뒤처지고(최대 −53 pulse) 컵이 수직선에서 4.6 mm 밀림. 하강·들기·칸 안 내리기·트레이 위 올리기도 같은 포화(뒤처짐 최대 93 pulse)로 수직 경로가 휨 | 고정 틱 느린 이동은 서보 속도 레지스터를 경로 속도(틱당 pulse ÷ 틱 시간, 기본 150)에 맞춤. 경로·가속 제한은 그대로 | 실행 기록으로 관절별 명령·실제 속도를 비교해 원인 확인, 모의 시험 통과. 고친 뒤 실물은 미확인 |

## 검증 결과 (실측값만)

![사이클 시간](portfolio/assets/cycle_time.png)

- 2026-10-20 시행 5회(흰 상자 2, 빨간 정육면체 2, 줄자 1): 실행 기록상 집기→놓기 사이클 완료 5/5, 해제 명령 5/5, 자동 HOME 복귀 5/5.
- 한 사이클은 53–83 s입니다. 접근·흡착·들기 25–32 s, 놓기 16–38 s, HOME 복귀 6–11 s가 걸렸습니다. 흰 상자는 1번 칸 벽을 피하려고 기울이는 단계가 있어 가장 깁니다.

## 한계

- 압력 센서가 없어 흡착을 직접 확인하지 못합니다. 손목 사진 판정은 한 조명·한 책상에서 맞춘 잠정 기준입니다.
- 색 기반 분류라 밝은 무채색 물체는 흰 상자와 구분하지 못합니다. 숫자 인식은 지금 필체에서만 확인했습니다.
- 새 물체는 높이 20–45 mm, 윗면이 평평한 것만 받습니다. 카메라가 높이를 3–5 mm 높게 재는 경향이 있고, 4축 팔은 물체를 돌릴 수 없어 놓이는 방향이 책상에 놓은 방향에 좌우되며, 칸 여유 5 mm 미만이어도 경고만 하고 실행합니다.
- 집기 가능한 반경은 약 0.16–0.30 m입니다. 이 범위 밖은 계획 단계에서 거부합니다.
- 하강·들기·칸 안 내리기는 서보 속도 상한을 풀어 설정 속도(150 pulse/s)로 실제 움직이게 됐습니다. 이전에는 실제 약 56–60 pulse/s였고, 흡착컵이 물체에 닿거나 칸 안으로 내려가는 구간을 이 속도로 실물 검증한 기록은 아직 없습니다. 흡착이 놓치면 `pick_auto.py --descent-rate`, `--held-rate`로 낮춥니다.
- 세 물체 연속 정리는 처음에 찍은 사진으로 세 물체 위치를 정합니다. 앞 물체를 집다가 옆 물체가 밀리면 다음 물체를 잘못 집을 수 있습니다.

## 실행

```bash
cd 4dof_ik
python scripts/sort_menu.py          # 번호 메뉴: 물체 분류기 (1~5 물체 넣기, 6 HOME 복귀, 7 새 물체 자동 집기)
python scripts/plan_sort.py --command "빨간 상자 3번 칸에 넣어줘"   # 카메라만 읽고 계획 출력
python scripts/run_sort.py --execute --supported --object red_cube  # 실제 구동 (재시도 포함)
```

**Raspberry Pi(로봇 위)로 옮기기**: [`pi/README.md`](pi/README.md) — 설치 스크립트(`pi/install.sh`), systemd 서비스, 장치 경로 설정(`ARM_*_PORT` 등), 노트북 음성 인식 서버(`scripts/stt_server.py`), 장치 점검(`scripts/check_devices.py`).

`--execute --supported` 없이 실행하면 로봇을 움직이지 않고 계획만 출력합니다. 개발 환경은 conda `lerobot_312`(Python 3.12)입니다.

**세 물체 모두 넣기(메뉴 4, 웹·REST `pick_all`)**는 연속으로 정리합니다.
1. 팔이 HOME에 있을 때 세 물체를 차례로 계획합니다(사진 3장, `run_sort.py --plan-out`). 팔은 움직이지 않습니다.
2. 놓은 뒤 HOME으로 돌아가지 않고 트레이 위에서 공구를 세운 채 섭니다(`pick_auto.py --skip-home-after-place`).
3. 다음 물체는 그 자리에서 높이 120mm 이상으로 올라가 극좌표 경로로 바로 갑니다(`--start-above-tray`, 저장한 계획 `--plan-in` 사용).
4. 마지막 물체만 HOME으로 복귀합니다. 시작 자세가 조건(높이 70–135mm, 반경 0.14–0.32m, 공구 수직, 기울여 집지 않음)을 벗어나면 기존처럼 HOME을 거쳐 갑니다.
5. 집기·놓기 실패 시에는 HOME으로 돌아가고 나머지는 하지 않습니다. 계획에 실패한 물체가 있으면 그 앞까지만 넣습니다.

## 웹 화면 · REST API · 대화(LLM) 조작

```bash
python scripts/arm_api.py                                  # 이 장비에서 http://127.0.0.1:8000 (웹 화면)
python scripts/arm_api.py --host 0.0.0.0 --token 비밀값     # 다른 장비(동료 웹 서버·휴대폰)에서 접속
```

- **웹 화면** (`/`): 물체 버튼, 물체·칸 선택, HOME 복귀, 진행 단계, 큰 정지 버튼, 대화 입력. 움직이는 명령은 항상 확인 창을 거친다.
- **상황 파악부터 시작**: 화면을 열면 먼저 위 카메라로 찍고(`POST /api/situation`) 책상 상황, 지금 쓸 수 있는 기능(예시 문장 포함), 기본 제안(정리할 물체가 있으면 책상 정리)을 알린 뒤 입력을 기다린다. 작업이 끝날 때마다 다시 찍어 알린다. 명령은 묻지 않고 바로 실행한다. 기본 제안은 "실행", "응", "정리해" 한마디로 시작한다(화면을 여는 것만으로는 움직이지 않는다).
- **책상 정리(기본 행동)**: "책상 정리해줘", "치워줘", "분류해줘", "다 정리해줘"처럼 물체 이름 없이 말하면 먼저 위 카메라로 찍어(get image와 같다) 책상에 있는 등록 물체 중 팔이 닿는 것만 담아 제안한다(`/api/menu/4`의 `objects`). 물체가 없으면 "정리할 물체가 없습니다", 등록 안 된 물체가 있으면 칸을 말해 달라고 알린다. 실행 중 계획에서 물체가 안 보이면 멈추지 않고 건너뛴다(NOMI 경로도 같다).
- **로봇 목소리**: 화면이 열려 있으면 답과 진행 상황을 소리로 알린다(어느 물체를 몇 번 칸에 넣는지, 마침·멈춤과 이유). NOMI가 시작한 작업도 알린다. 브라우저 음성 합성을 쓰고 한국어 음성을 골라 쓴다(구글 음성, 없으면 이 PC의 espeak-ng).
- **음성**: 화면의 [말하기](또는 입력칸 밖에서 스페이스)를 누르고 말한다. 기본은 로컬 인식(`POST /api/stt`, 이 PC의 faster-whisper `small`, CPU에서 한 문장 약 1초, 인터넷 불필요)이고, 브라우저(구글) 인식도 고를 수 있다. 알아들은 문장은 대화와 같이 처리한다. "멈춰/정지/그만"은 바로 멈추고, 움직이는 명령은 묻지 않고 바로 실행한다. 마이크는 브라우저 보안상 `http://localhost:8000` 또는 https 주소에서만 열린다. 서버에 `pip install faster-whisper`가 필요하다(없으면 로컬 인식만 꺼진다).
- **대화**: 로컬 LLM(Ollama, 기본 `qwen3.5:9b`)이 말을 도구 호출(`sort_object`, `sort_all_objects`, `arm_return_home`, `look_at_table`, `get_arm_status`, `stop_arm`)로 바꾼다. 상태 확인·사진 찍기·정지는 바로 실행하고, 넣기·복귀는 제안만 해서 화면에서 [실행]을 눌러야 움직인다. Ollama가 켜져 있고 모델이 받아져 있어야 한다(`ollama pull qwen3.5:9b`). 추가 패키지는 필요 없고, 꺼져 있으면 대화만 `503 llm_unavailable`이고 버튼은 동작한다. 주소·모델은 `OLLAMA_HOST`, `ARM_LLM_MODEL`로 바꾼다. 첫 요청은 모델을 올리느라 1분쯤 걸릴 수 있다(`ARM_LLM_TIMEOUT`, 기본 120초).

| 요청 | 설명 |
|---|---|
| `POST /robot_arm` `{"action": "pick_place", "object": "red_cube", "slot": 2}` | LLM 도구 호출 모양 그대로. action: `pick_place` · `return_home` · `status` · `stop` |
| `POST /pick_place`, `POST /return_home`, `POST /stop` | 개별 주소(같은 동작). 움직이는 명령은 바로 `202 {"task_id"}` |
| `GET /status` · `GET /tasks/<id>` | 진행 단계(`phase_label`)·결과(`ok`, `reason_code`, `warnings`) |
| `POST /chat` `{"history": [...], "text": "..."}` | 대화 → `{"reply", "proposal", "executed", "scene"}` |

object: `white_box`(1번) · `red_cube`(2) · `tape_measure`(3) · `unknown`(새 물체, `phase`가 `unknown_wait`일 때 물체를 놓는다). 한 번에 한 작업만 받고(실행 중이면 `409 busy`), 토크가 꺼져 있으면 움직이지 않는다(`torque_off`). 동료 웹 서버가 대신 부르면 CORS 설정은 필요 없고, 브라우저에서 직접 부르면 `--cors-origin http://주소`를 준다. LLM 도구 정의는 `scripts/arm_llm.py`의 `TOOLS`.
